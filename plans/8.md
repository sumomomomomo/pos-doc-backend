# Task 8: Local first-page OCR through the existing llama.cpp service

## Objective

Implement the production-quality internal OCR boundary that sends the temporary first-page PNG produced by Task 7 to the already-running llama.cpp-compatible service on the private LAN.

The service is outside this repository and is assumed to be continuously available at:

```text
http://192.168.1.34:8080
```

The backend must:

1. Accept a persisted `pos_document` UUID.
2. Call the existing `FirstPageRenderPreparationService.prepare(documentId)` exactly once.
3. Stream the resulting temporary PNG into one bounded `POST /v1/chat/completions` request.
4. Select the exact model reported by the service.
5. Validate and bound the HTTP response.
6. Return an immutable, ephemeral OCR result containing the recognized text and safe model metadata.
7. Close the Task 7 `RenderedFirstPage` handle on every success and failure path.

This task establishes and tests the OCR HTTP boundary only. It must not yet invoke OCR from RabbitMQ, classify documents, extract policy fields, update document/job status, or persist OCR output.

## Required outcome

```text
documentId
  -> FirstPageRenderPreparationService.prepare(documentId)
  -> owned temporary PNG
  -> bounded streaming base64 data URL
  -> POST http://192.168.1.34:8080/v1/chat/completions
  -> bounded and validated response
  -> close/delete temporary PNG
  -> return ephemeral OcrResult
```

No PNG or OCR text may remain in MinIO, SQLite, logs, exception messages, HTTP endpoints, RabbitMQ messages, or temporary files after the call returns.

## External protocol decision

Use llama.cpp's OpenAI-compatible Chat Completions endpoint. llama.cpp supports typed multimodal chat content and accepts base64 data URLs in `image_url.url`.

Send this logical JSON shape:

```json
{
  "model": "/models/dotsmocr-1.8b-q8_0.gguf",
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "type": "image_url",
          "image_url": {
            "url": "data:image/png;base64,<STREAMED_BASE64>"
          }
        },
        {
          "type": "text",
          "text": "Extract the text content from this image."
        }
      ]
    }
  ],
  "temperature": 0.1,
  "top_p": 0.9,
  "max_tokens": 4096,
  "n": 1,
  "stream": false
}
```

Important details:

- Use `max_tokens`, not `max_completion_tokens`.
- The prompt text is exactly `Extract the text content from this image.`
- Do not put `<|img|>`, `<|imgpad|>`, `<|endofimg|>`, or any other model-control token in the text. llama.cpp owns multimodal chat-template formatting for an `image_url` content part.
- Preserve the content-part order shown above: image first, text second.
- Do not use `/v1/completions`, the Responses API, multipart upload, a public image URL, a presigned MinIO URL, or a filesystem URL.
- Do not send an `Authorization` header. The supplied server contract does not specify authentication. Do not invent a dummy bearer token.

Implementer reference:

- llama.cpp server documentation: `https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md`
- The relevant documented routes are `GET /v1/models` and `POST /v1/chat/completions`; the multimodal request format uses an `image_url` content part whose URL may be a base64 data URI.

## `StreamingPngChatRequestBody`

Implement an OkHttp `RequestBody` responsible only for serializing the fixed JSON request while streaming the PNG as base64.

Required behavior:

1. Accept `Path pngPath`, expected PNG byte count, model, prompt, and fixed generation parameters.
2. Before writing, call `Files.size(pngPath)` and require that the size is positive, equals `RenderedFirstPage.pngByteSize()`, and is no greater than `max-image-bytes`.
3. Write a fixed JSON prefix with model and prompt values escaped using the existing Jackson `ObjectMapper`; never interpolate an unescaped string into JSON.
4. Write `data:image/png;base64,`.
5. Stream the file through `Base64.getEncoder().wrap(...)` using an 8192-byte buffer.
6. Wrap the OkHttp sink output stream in a non-closing output-stream adapter so closing the Base64 encoder writes final padding without closing the HTTP sink.
7. Count raw PNG bytes during streaming and abort if the count exceeds the expected size or `max-image-bytes`.
8. Validate that the first eight raw bytes equal the PNG signature `89 50 4E 47 0D 0A 1A 0A`, while still including those bytes in the base64 stream.
9. At EOF, require the raw byte count to equal the expected size. This detects replacement or truncation between the initial size check and transmission.
10. Write the fixed JSON suffix and flush it.
11. Return `-1` from `contentLength()` so OkHttp uses streaming/chunked transfer. Do not pre-encode the PNG merely to calculate content length.

The JSON prefix and suffix are small and may be held as UTF-8 byte arrays. The PNG and its complete base64 representation may not be held in memory.

Use a dedicated internal exception for raw-image size or stream failures so `LlamaCppOcrClient` can distinguish local image/storage failures from remote HTTP failures. Exception messages must not contain the path or bytes. The class must not expose the PNG path through `toString()`.

## `LlamaCppOcrClient`

Expose one method:

```java
OcrResult recognize(RenderedFirstPage page)
```

Required flow:

1. Reject `null`.
2. Acquire a fair semaphore with exactly one permit.
3. If interrupted while waiting, restore the interrupt flag and throw `OCR_INTERRUPTED` without closing the page; page ownership remains with `FirstPageOcrService`.
4. Build the fixed request using `StreamingPngChatRequestBody`.
5. Execute it synchronously with the shared OkHttp client.
6. Release the semaphore in `finally`, including request construction, network, response validation, and interruption failures.
7. Close the OkHttp `Response` and response body on every path.

Do not retry inside this client. A later queue workflow will own retry policy.

### HTTP status mapping

Map status codes exactly:

| Status | Code | Retryable |
|---|---|---:|
| `200` | continue response validation | — |
| `400`, `404`, `405`, `409`, `415`, `422` | `OCR_REQUEST_REJECTED` | No |
| `401`, `403` | `OCR_AUTH_FAILED` | No |
| `408`, `429` | `OCR_SERVICE_BUSY` | Yes |
| `500`–`599` | `OCR_SERVICE_UNAVAILABLE` | Yes |
| redirects and every other status | `OCR_PROTOCOL_ERROR` | No |

Keep `OCR_AUTH_FAILED` even though the current server is unauthenticated; it provides a stable mapping if the server or a network gateway rejects the request. Do not include the remote response body, reason phrase, URL, headers, or server error text in exceptions or logs.

### Bounded response reading

For a `200` response:

- Require a response body.
- Require a JSON-compatible content type (`application/json` or `application/*+json`), ignoring parameters such as charset.
- Wrap the response stream in a bounded input stream that throws before more than `max-response-bytes` are consumed.
- Parse directly from the bounded stream with Jackson. Do not first convert the whole body to a string or byte array.
- Reject trailing non-whitespace content after the root JSON object.
- Require exactly one entry in `choices`.
- Require `choices[0].message.role == "assistant"` if role is present.
- Require `choices[0].message.content` to be a JSON string, nonblank, and no longer than `max-ocr-characters`.
- Require response `model` to equal `/models/dotsmocr-1.8b-q8_0.gguf`.
- Require `finish_reason == "stop"`.
- Treat `finish_reason == "length"` as `OCR_OUTPUT_TRUNCATED`.
- Treat null, blank, unknown, or non-string finish reasons as `OCR_RESPONSE_INVALID`.
- Ignore unknown JSON fields such as llama.cpp's `timings` for forward compatibility.
- Do not require `usage`; if present, validate only that token counts are non-negative. Do not return or persist them.

## Stable errors

Implement `OcrException` with a fixed enum/code, fixed safe message, and retryable flag.

Include exactly these codes:

| Code | Retryable | Meaning |
|---|---:|---|
| `OCR_IMAGE_INVALID` | No | PNG metadata, signature, or size is invalid |
| `OCR_IMAGE_UNAVAILABLE` | Yes | Temporary PNG cannot be opened or read |
| `OCR_INTERRUPTED` | Yes | Interrupted while waiting or executing |
| `OCR_TIMEOUT` | Yes | Connect, read, or call timeout |
| `OCR_SERVICE_BUSY` | Yes | HTTP 408 or 429 |
| `OCR_SERVICE_UNAVAILABLE` | Yes | Connection failure or HTTP 5xx |
| `OCR_AUTH_FAILED` | No | HTTP 401 or 403 |
| `OCR_REQUEST_REJECTED` | No | Supported nonretryable 4xx response |
| `OCR_PROTOCOL_ERROR` | No | Redirect, unexpected status, or invalid content type |
| `OCR_RESPONSE_TOO_LARGE` | Yes | Response exceeds configured byte limit |
| `OCR_RESPONSE_INVALID` | No | Malformed or structurally invalid successful response |
| `OCR_OUTPUT_EMPTY` | No | Successful response contains no OCR text |
| `OCR_OUTPUT_TRUNCATED` | No | Model stopped because token limit was reached |

There is deliberately no `OCR_DISABLED` code.

Mapping details:

- `InterruptedIOException` caused by OkHttp interruption maps to `OCR_INTERRUPTED` when the thread is interrupted; otherwise map timeout exceptions by type, not arbitrary message text.
- Connect, read, and call timeout exceptions map to `OCR_TIMEOUT`.
- Connection refusal, reset, and other transport I/O map to `OCR_SERVICE_UNAVAILABLE`.
- Local request-body PNG open/read failures map to `OCR_IMAGE_UNAVAILABLE`, not service unavailable.
- Size or metadata mismatches discovered by the request body map to `OCR_IMAGE_INVALID`.
- Jackson syntax/type failures map to `OCR_RESPONSE_INVALID`.

Never expose raw exception messages. Preserve causes internally where useful.
