# Task 3: SQLite persistence model and migrations

## Objective

Replace the absence of a persistence model with a real, migration-controlled SQLite schema and a tested Spring Data JPA persistence layer.

This task creates the durable metadata foundation needed by later upload, RabbitMQ, PDF extraction, OCR, and search tasks. It does **not** connect persistence to the generated HTTP API yet. All Task 1 HTTP endpoints must continue returning their existing deterministic dummy data.

This task is complete only when every command in **Verification order** succeeds.

## Step 2: Define the initial migration

Create exactly one initial migration:

```text
src/main/resources/db/migration/V1__create_persistence_schema.sql
```

Use ordinary SQLite SQL. Do not put `PRAGMA foreign_keys`, `BEGIN`, `COMMIT`, or rollback commands inside the migration. The existing datasource configuration owns connection PRAGMAs, and Flyway owns transactions.

Create the following four tables. Use the column names and nullability below exactly unless SQLite requires a harmless syntax adjustment.

### `storage_object`

| Column | SQLite type | Rules |
|---|---:|---|
| `id` | `TEXT` | Primary key; UUID string |
| `object_key` | `TEXT` | Not null; unique |
| `original_filename` | `TEXT` | Not null; length validated by Java |
| `content_type` | `TEXT` | Not null |
| `byte_size` | `INTEGER` | Not null; check `byte_size >= 0` |
| `sha256` | `TEXT` | Not null; check length is 64 |
| `created_at_epoch_ms` | `INTEGER` | Not null |

Do not make `sha256` unique. Two separate uploads may contain identical bytes.

### `pos_record`

| Column | SQLite type | Rules |
|---|---:|---|
| `id` | `TEXT` | Primary key; UUID string |
| `source_archive_id` | `TEXT` | Not null; unique; foreign key to `storage_object(id)` with `ON DELETE RESTRICT` |
| `eref_number` | `TEXT` | Nullable; original display value |
| `eref_number_normalized` | `TEXT` | Nullable |
| `policy_number` | `TEXT` | Nullable; original display value |
| `policy_number_normalized` | `TEXT` | Nullable |
| `policyholder_name` | `TEXT` | Nullable |
| `policyholder_name_normalized` | `TEXT` | Nullable |
| `consultant_name` | `TEXT` | Nullable |
| `policy_create_date` | `TEXT` | Nullable ISO-8601 date |
| `status` | `TEXT` | Not null |
| `uploaded_by` | `TEXT` | Not null; stable subject identifier |
| `uploaded_at_epoch_ms` | `INTEGER` | Not null |
| `updated_at_epoch_ms` | `INTEGER` | Not null |
| `deleted_at_epoch_ms` | `INTEGER` | Nullable; non-null means soft-deleted |
| `version` | `INTEGER` | Not null; check `version >= 0` |

Add check constraints limiting `status` to:

```text
UPLOADED
VALIDATING
PROCESSING
REVIEW_REQUIRED
COMPLETED
FAILED
```

Add these partial unique indexes:

```sql
CREATE UNIQUE INDEX uq_pos_record_active_eref
    ON pos_record (eref_number_normalized)
    WHERE deleted_at_epoch_ms IS NULL
      AND eref_number_normalized IS NOT NULL;

CREATE UNIQUE INDEX uq_pos_record_active_policy
    ON pos_record (policy_number_normalized)
    WHERE deleted_at_epoch_ms IS NULL
      AND policy_number_normalized IS NOT NULL;
```

Add a non-unique index on `policyholder_name_normalized`. Do not implement trigram or fuzzy matching in SQLite in this task.

## Step 3: Implement deterministic converters

### `InstantEpochMillisConverter`

Implement a JPA `AttributeConverter<Instant, Long>`:

- `Instant` to database: epoch milliseconds
- Database to `Instant`: `Instant.ofEpochMilli(value)`
- Preserve `null`
- Mark it `autoApply = true`

### `LocalDateIsoConverter`

Implement a JPA `AttributeConverter<LocalDate, String>`:

- `LocalDate` to database: `DateTimeFormatter.ISO_LOCAL_DATE`
- Database to `LocalDate`: parse the same exact format
- Preserve `null`
- Mark it `autoApply = true`

Do not use the host timezone for either conversion.

## Step 5: Implement normalization

Create `MetadataNormalizer` as a stateless utility or Spring component with no database or network dependency.

It must implement exactly these operations:

```java
String normalizeIdentifier(String value)
String normalizeName(String value)
```

Both methods return `null` for `null`. Both reject an input that becomes empty after normalization with `IllegalArgumentException`.

### Identifier normalization

For eRef and policy numbers, in this exact order:

1. Apply Unicode NFKC normalization.
2. Convert to uppercase with `Locale.ROOT`.
3. Keep only Unicode letters and decimal digits.

Examples:

```text
" EREF-2026 001 " -> "EREF2026001"
"p-123/45"       -> "P12345"
```

### Name normalization

For policyholder names, in this exact order:

1. Apply Unicode NFKC normalization.
2. Trim leading and trailing Unicode whitespace.
3. Convert to lowercase with `Locale.ROOT`.
4. Collapse every run of Unicode whitespace to one ASCII space.

Do not remove accents, punctuation, or non-Latin characters from names.

Examples:

```text
"  Jane   TAN " -> "jane tan"
"José Lim"      -> "josé lim"
```

Write focused unit tests for `null`, blank input, Unicode compatibility characters, case conversion, punctuation handling, and whitespace collapsing.

## Step 6: Implement entities

General rules for every entity:

- Use field access consistently.
- Provide a protected no-argument constructor for JPA.
- Provide an explicit constructor or factory for required fields.
- Do not use Lombok.
- Do not use public mutable fields.
- Do not include PII, credentials, error messages, or object keys in `toString()`.
- Do not implement `equals`/`hashCode` using mutable fields or relationships.
- Store UUID identifiers in `TEXT` columns. Use Hibernate's explicit VARCHAR JDBC mapping for `UUID` fields, for example `@JdbcTypeCode(SqlTypes.VARCHAR)`.
- Generate UUIDs in application code before first persistence. Do not rely on a SQLite UUID function.
- Apply `@Version` to the `version` fields in `PosRecordEntity` and `IngestionJobEntity`.
- Use `@Enumerated(EnumType.STRING)` for enums.
- Match migration column names explicitly with `@Column`.
- Do not use `CascadeType.REMOVE`.
- Do not use `orphanRemoval = true`.
- Keep relationships lazy unless a test proves eager loading is required.

## Step 10: Add persistence tests

Use JUnit 5, Spring Boot's real application context, the real repositories, and a unique temporary SQLite file for each test class.

Do not mock JPA, repositories, Flyway, the datasource, or SQLite.

Use `@DirtiesContext(classMode = AFTER_CLASS)` and the cleanup rules above.

### `MigrationIntegrationTest`

Prove:

1. Flyway runs on a clean temporary SQLite database.
2. `flyway_schema_history` exists.
3. Exactly migration version `1` is successful.
4. The four required business tables exist.
5. All declared foreign keys are enabled and present.
6. The two partial unique indexes exist.
7. Hibernate does not create extra business tables.

Query SQLite metadata through `JdbcTemplate`; do not infer migration success merely because the Spring context started.

### `PosRecordRepositoryIntegrationTest`

Use a new storage object and POS record per test unless a test explicitly requires two records.

Prove:

1. A record saves and loads with UUIDs, enums, dates, timestamps, and relationships unchanged.
2. eRef lookup uses the normalized value.
3. Policy-number lookup uses the normalized value.
4. Two active records with display-different but normalization-equivalent eRefs cause a database uniqueness failure on `saveAndFlush`.
5. Two active records with normalization-equivalent non-null policy numbers cause a database uniqueness failure on `saveAndFlush`.
6. Multiple active records may have `NULL` policy numbers.
7. A soft-deleted record is absent from active lookup methods but remains available through inherited `findById`.
8. An eRef and policy number may be reused by a new active record after the old record is soft-deleted and flushed.
9. Updating an entity increments its `@Version` value.
10. Two independently loaded copies followed by conflicting writes cause an optimistic-locking exception.

For constraint tests, flush inside the assertion. A test that never flushes does not prove SQLite enforced the constraint.

Clear the persistence context between independent loads when testing optimistic locking.

### `PersistenceRelationshipsIntegrationTest`

Prove:

1. One archive storage object can be attached to one POS record.
2. Multiple PDF storage objects and `pos_document` rows can belong to one POS record.
3. Documents load in ascending `sequenceNumber` order.
4. Multiple ingestion jobs can belong to one POS record and load in ascending `createdAt` order.
5. Reusing the same storage object for two source archives is rejected.
6. Reusing the same PDF storage object for two document rows is rejected.
7. A document referencing a nonexistent POS record is rejected by SQLite's foreign-key constraint.
8. Deleting referenced storage metadata is rejected rather than cascading into POS metadata.

Use repositories for normal persistence tests. A small `JdbcTemplate` statement is allowed only where constructing an impossible JPA relationship is necessary to prove a raw foreign-key constraint.
