## Objective

Replace the remaining Task 1 dummy POS-record operations with a real SQLite-backed API suitable for a later frontend review page.

At the end of Task 10, an HTTP client must be able to:

1. Fetch a persisted POS record.
2. Search active POS records with deterministic pagination and sorting.
3. Correct the record's editable metadata using optimistic concurrency.
4. Explicitly verify a `REVIEW_REQUIRED` record and move it to `COMPLETED`.
5. Soft-delete a record.
6. Fetch the real ingestion job and list the real extracted PDF metadata without regressing the already-working implementations.

Task 10 is an API/read-model/review-state task. It does **not** extract structured policy fields from OCR text. For now, a human or test client supplies corrections through the PATCH endpoint.

## Metadata PATCH semantics

The existing `PosRecordPatch` contains `expectedVersion` plus these editable properties:

- `erefNumber`
- `policyNumber`
- `policyholderName`
- `consultantName`
- `policyCreateDate`

Implement these exact rules:

1. `expectedVersion` is mandatory and must be non-negative.
2. At least one editable property must contain a non-null value. A body containing only `expectedVersion` is `400 NO_PATCH_FIELDS`.
3. Omitted/null Java properties mean unchanged. Task 10 does not support clearing a value to SQL `NULL`.
4. Trim and validate display values through the existing entity mutators/`MetadataNormalizer`; never write normalized columns independently.
5. Blank strings are invalid, not a request to clear data.
6. Preserve user-facing spelling/casing in display columns while using the repository's normalized form for uniqueness and search.
7. The client may not change IDs, status directly, source storage, uploader, timestamps, deleted state, document rows, job rows, or OCR rows.
8. Set `updatedAt` using an injected `Clock`; do not trust a client timestamp or the host default timezone.
9. If the record was `COMPLETED` and any editable field actually changes, move it back to `REVIEW_REQUIRED`. A human must verify the corrected values again.
10. If a submitted value equals the persisted normalized/display value and no other field changes, return the current record without manufacturing a state transition. The version may remain unchanged for this no-op.
11. PATCH is allowed only while the active record is `REVIEW_REQUIRED` or `COMPLETED`. Other states return `409 POS_RECORD_NOT_REVIEWABLE`.

Because the generated DTO represents omitted and explicit JSON `null` the same way in this project, both mean unchanged. Document this behavior in the OpenAPI PATCH description; do not build a custom JSON parser solely to distinguish them.

### Uniqueness

The existing active-record uniqueness rules remain authoritative:

- normalized non-null eRef is unique among records where `deleted_at IS NULL`;
- normalized non-null policy number is unique among records where `deleted_at IS NULL`.

Translate conflicts to sanitized `409` Problems:

- `DUPLICATE_EREF_NUMBER`
- `DUPLICATE_POLICY_NUMBER`

A pre-check may improve the error, but it does not replace the database constraint. Handle the race at flush/commit. If a `DataIntegrityViolationException` occurs, perform safe normalized existence checks to select the stable code; never return the SQLite exception text or conflicting PII.

## Optimistic concurrency

Use the existing `@Version` field. Do not invent another revision column.

For PATCH and verification:

1. Load the active record in a transaction.
2. Compare the request `expectedVersion` with the entity version.
3. If they differ, return `412 POS_RECORD_VERSION_MISMATCH`.
4. Mutate and flush within that transaction.
5. Translate an optimistic-lock exception caused by a concurrent commit to the same sanitized `412` result.

Return the new persisted version in the successful `PosRecord` body. Do not use `409` for a version mismatch because the current OpenAPI contract already defines `412 Precondition Failed` for this case.

## Verification semantics

`POST /pos-records/{id}/verification` is the only Task 10 operation that moves a record from `REVIEW_REQUIRED` to `COMPLETED`.

Apply these checks in one short database transaction:

1. The record exists and is not soft-deleted; otherwise `404 POS_RECORD_NOT_FOUND`.
2. `expectedVersion` matches; otherwise `412 POS_RECORD_VERSION_MISMATCH`.
3. Current status is `REVIEW_REQUIRED`; otherwise `409 POS_RECORD_NOT_REVIEWABLE`.
4. At least one `pos_document` belongs to the record.
5. Every document is `COMPLETED`.
6. The associated ingestion job is `COMPLETED`.
7. `erefNumber`, `policyNumber`, `policyholderName`, and `consultantName` are all nonblank after normalization.

`policyCreateDate` remains optional because not every document will yield one reliably.

If checks 4â€“7 fail, return `422 POS_RECORD_INCOMPLETE` with a fixed sanitized detail. Do not include field values, OCR text, filenames, or storage identifiers in the error.

On success:

- set status to `COMPLETED`;
- update `updatedAt` from the injected clock;
- flush so the response contains the incremented version;
- return the mapped `PosRecord` with HTTP `200`.

Repeated verification with the old or new version is not silently idempotent: because the state is no longer `REVIEW_REQUIRED`, return `409 POS_RECORD_NOT_REVIEWABLE`. This makes accidental double submission visible to the frontend.

Verification must not call MinIO, RabbitMQ, PDF rendering, or OCR.

## Soft delete semantics

`DELETE /pos-records/{id}` must call the entity's existing idempotent soft-delete behavior inside a transaction and update the record timestamp consistently.

- An active record is soft-deleted and returns `204` with no response body.
- A missing or already-soft-deleted record returns `404 POS_RECORD_NOT_FOUND`.
- Do not physically delete the POS row, storage row, ZIP, PDFs, documents, jobs, outbox rows, or OCR results.
- Do not publish a RabbitMQ message.
- Once deleted, the record must disappear from detail, search, document-list, and job-read endpoints.
- Existing normalized eRef and policy-number partial unique indexes must allow those values to be reused by a new active record after deletion.
- A concurrent optimistic-lock failure during deletion returns sanitized `409 POS_RECORD_DELETE_CONFLICT`; do not add a request body or version header to DELETE in this task.

## Search behavior

Implement the existing `POST /pos-records/search` contract exactly. An empty `{}` request lists all active records using the defaults.

### Defaults and validation

- `page`: default `0`
- `size`: default `20`, maximum `100`
- `fuzzyName`: default `true`
- `minimumNameSimilarity`: default `0.3`
- `sort`: default `RELEVANCE`
- missing or empty `statuses`: no status filter

Reject invalid page, size, threshold, blank search strings, or unsupported sort values as `400 INVALID_SEARCH_REQUEST`. Bean Validation generated from OpenAPI should handle what it can; service-layer validation must protect direct calls too.

### Filter semantics

- Exclude every record with non-null `deletedAt` before all other filtering.
- eRef uses exact equality after the existing eRef normalization.
- Policy number uses exact equality after the existing policy-number normalization.
- Policyholder name uses the same normalized value stored by the entity.
- Status matching is membership in the requested set.
- Multiple supplied filters are combined with logical **AND**.
- Do not search consultant name, filenames, storage metadata, OCR text, or errors in Task 10.

When `policyholderName` is present:

- if `fuzzyName` is false, require exact normalized-name equality;
- if `fuzzyName` is true, calculate the deterministic trigram similarity below and retain scores greater than or equal to `minimumNameSimilarity`.

### Exact trigram algorithm

Implement one small tested utility named descriptively, such as `TrigramSimilarity`. Do not add Elasticsearch or a native SQLite extension.

1. Receive already-normalized, nonblank strings.
2. Pad each entire string with two ASCII spaces on both sides.
3. Produce the set of distinct consecutive three-character substrings, iterating by Unicode code point rather than UTF-16 code unit.
4. Return `1.0` when the two normalized strings are equal.
5. Otherwise return the SÃ¸rensenâ€“Dice score: `2 * intersectionSize / (leftSetSize + rightSetSize)`.
6. Clamp only numerical roundoff to `[0.0, 1.0]`.

Do not use locale-dependent comparison or the host default locale.

Given the expected volume (roughly 800â€“1,000 records per year), it is acceptable to load the active rows matching the exact/status filters, score normalized names in Java, sort deterministically, and then page the result. Do not load associated storage objects or OCR result text for search.

### Deterministic sort rules

Apply the requested sort with UUID ascending as the final tie-breaker:

| Sort | Ordering |
|---|---|
| `RELEVANCE` with fuzzy/exact name query | similarity descending, `updatedAt` descending, ID ascending |
| `RELEVANCE` without a name query | `updatedAt` descending, ID ascending |
| `UPLOADED_AT_DESC` | `uploadedAt` descending, ID ascending |
| `UPLOADED_AT_ASC` | `uploadedAt` ascending, ID ascending |
| `UPDATED_AT_DESC` | `updatedAt` descending, ID ascending |
| `UPDATED_AT_ASC` | `updatedAt` ascending, ID ascending |

Do not expose the similarity score in the API in Task 10 because the existing `PosRecordSummary` has no score property.

Apply pagination **after** all filters and sorting. Compute:

- `totalElements`: count after filters, before paging;
- `totalPages`: `0` when total is zero, otherwise ceiling of `totalElements / size`;
- `items`: empty when the requested page starts beyond the result count.

Search summaries contain the persisted display metadata and timestamps defined by the current `PosRecordSummary`; they must not contain only IDs.

## Application structure

Keep controllers thin. A suitable decomposition is:

- `PosRecordReadService`: active detail read and DTO-ready entity load
- `PosRecordSearchService`: validation, normalized filtering, scoring, sorting, and paging
- `PosRecordCommandService`: PATCH, verification, and soft delete
- `IngestionJobReadService`: active job lookup
- API mapper(s): entity/read projection to generated DTOs

The exact class names may follow existing package conventions, but do not put business logic or transaction orchestration in controllers.

Transaction requirements:

- Detail/job/document reads: `@Transactional(readOnly = true)` at service boundaries.
- Search candidate loading: read-only transaction; complete all lazy-safe projection data before returning.
- PATCH, verification, and delete: one short transaction each.
- No transaction in Task 10 may include MinIO, RabbitMQ, OCR, rendering, or network I/O.

Prefer repository queries/projections that exclude soft-deleted records by construction. Do not call unrestricted `findById` in a public read path and then forget the deletion check.

## Error handling

Use the existing `ApiExceptionHandler` and generated `Problem` shape. Add a narrowly scoped application exception/code mapping if the current intake exception does not represent these API errors cleanly.

Required stable codes:

| HTTP status | Code | Situation |
|---|---|---|
| 400 | `INVALID_SEARCH_REQUEST` | Invalid search/page/sort/threshold |
| 400 | `NO_PATCH_FIELDS` | PATCH has no actual editable value |
| 404 | `POS_RECORD_NOT_FOUND` | Record missing or soft-deleted |
| 404 | existing sanitized job-not-found code | Job missing or parent record deleted |
| 409 | `DUPLICATE_EREF_NUMBER` | Active normalized eRef conflict |
| 409 | `DUPLICATE_POLICY_NUMBER` | Active normalized policy conflict |
| 409 | `POS_RECORD_NOT_REVIEWABLE` | PATCH/verification forbidden in current state |
| 409 | `POS_RECORD_DELETE_CONFLICT` | Concurrent delete/update conflict |
| 412 | `POS_RECORD_VERSION_MISMATCH` | Stale expected version or concurrent command |
| 422 | `POS_RECORD_INCOMPLETE` | Verification prerequisites are not met |

All error details must be fixed/sanitized. Never copy request values, entity `toString()`, SQL messages, OCR output, response bodies, filenames, object keys, or filesystem paths into a `Problem`, exception message, or log.

Malformed UUIDs and request-body validation must continue producing `application/problem+json`, not Spring's default HTML or an unstructured response.

## PII and logging rules

Treat eRef, policy number, policyholder name, consultant name, filenames, and OCR text as sensitive.

- Do not log search criteria or PATCH bodies.
- Do not log response DTOs or entities containing display metadata.
- Safe identifiers such as POS-record UUID, job UUID, stable error code, status, page number, and result count may be logged at appropriate levels.
- Do not add SQL parameter logging.
- Keep entity `toString()` PII-safe.
