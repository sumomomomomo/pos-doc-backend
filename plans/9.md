# Task 9: Integrate OCR into the ingestion workflow and persist per-document results

## Objective

Connect the three production stages that already exist:

```text
Task 6: ZIP extraction and persisted pos_document rows
    -> Task 7: bounded first-page PDF rendering
    -> Task 8: local OCR through FirstPageOcrService
    -> durable per-document OCR result
```

The existing RabbitMQ ingestion message must remain the single workflow trigger. A successful ingestion must OCR every extracted PDF, persist one OCR result for each document for prompt version 1, and then complete the ingestion job.

Task 8 deliberately kept OCR results ephemeral. Task 9 is the first task allowed to persist OCR text and invoke OCR from the RabbitMQ workflow.

The forward-looking sentence in `plans/8.md` that assigns classification and structured field extraction to Task 9 is superseded by this plan. Those concerns are deliberately deferred to Task 10.

## Required successful flow

```text
Existing ingestion message
    -> validate message and archive as already implemented
    -> extract PDFs as already implemented
    -> load persisted documents in deterministic sequence order
    -> for each document not already OCR-complete for prompt version 1:
         mark document PROCESSING in a short transaction
         call FirstPageOcrService.recognize(documentId) outside a transaction
         persist OCR result and mark document COMPLETED in a short transaction
    -> mark ingestion job COMPLETED
    -> move the POS record to REVIEW_REQUIRED
    -> acknowledge the existing RabbitMQ message
```

`REVIEW_REQUIRED` means that durable OCR exists but structured policy metadata has not yet been extracted or verified. Do not mark the POS record `COMPLETED` in Task 9.

## Database migration

Do not edit `V1`. Add the next correctly numbered Flyway migration and create exactly one new table named `document_ocr_result`.

Required columns:

| Column | SQLite representation | Requirements |
|---|---|---|
| `document_id` | `TEXT` | Non-null foreign key to `pos_document(id)` |
| `prompt_version` | `INTEGER` | Non-null and positive; Task 9 uses `1` |
| `ocr_text` | `TEXT` | Non-null, nonblank, at most 1,000,000 characters |
| `model` | `TEXT` | Non-null and nonblank |
| `finish_reason` | `TEXT` | Non-null and nonblank |
| `character_count` | `INTEGER` | Non-negative and equal to SQLite `length(ocr_text)` |
| `completed_at` | `INTEGER` | Non-null UTC epoch milliseconds |

Use `(document_id, prompt_version)` as the primary key. Use `ON DELETE RESTRICT` for the document foreign key. Do not add a surrogate UUID.

Add check constraints for the requirements expressible in SQLite, including:

- `prompt_version > 0`
- `length(trim(ocr_text)) > 0`
- `length(ocr_text) <= 1000000`
- nonblank model and finish reason
- `character_count = length(ocr_text)`

Do not add policy fields or searchable OCR indexes in this migration. Raw OCR text is not a search surface.

## Persistence model

Create a JPA entity mapped to `document_ocr_result` and a repository for it.

Requirements:

- Represent the composite key explicitly with the repository's established JPA style (`@EmbeddedId` or `@IdClass`). Do not invent a surrogate ID.
- Map `document_id` as UUID-backed text consistently with the existing entities.
- Map `completed_at` through the existing UTC `Instant` converter.
- Associate the result with `PosDocumentEntity` lazily.
- The entity must enforce the same non-null, nonblank, length, prompt-version, and character-count invariants before persistence.
- `ocr_text` may be returned to internal application code.
- `toString()`, exception messages, logs, `equals()`, and `hashCode()` must never include OCR text.
- `toString()` may include document ID, prompt version, model, finish reason, character count, and completion time.
- Avoid Lombok-generated `toString`, `equals`, or `hashCode` if they would include the OCR text or lazy association.

The repository must support, at minimum:

```text
find by document ID and prompt version
existence by document ID and prompt version
count by POS record ID and prompt version
```

The count query may join through `PosDocumentEntity`, but it must not load OCR text merely to count rows.

## Prompt version

Task 9 processes prompt version `1`, matching Task 8.

- Define this value once in the new workflow layer as a named constant.
- Assert that every returned `OcrResult.promptVersion()` equals that value before persistence.
- A result for a different prompt version does not make version 1 complete.
- Do not silently overwrite a result for the same `(document_id, prompt_version)`.
- A future task may deliberately create another version; Task 9 must not delete historical versions.

## Transaction boundaries

SQLite transactions must never remain open during:

- MinIO access
- PDF loading or rendering
- Temporary-file creation or deletion
- HTTP calls to llama.cpp
- RabbitMQ waiting or backoff

Implement a small transaction-bound persistence service with separate public methods for state changes. The workflow service itself must not be annotated `@Transactional`.

Required transaction pattern for one document:

1. In a short transaction, inspect the document and version-1 OCR-result state.
2. If the version-1 result already exists, make the document status consistent with completion and return `ALREADY_COMPLETED` without calling OCR.
3. Otherwise, change `PENDING` or stale `PROCESSING` to `PROCESSING` and commit.
4. Call `FirstPageOcrService.recognize(documentId)` outside a transaction.
5. In a new short transaction, validate and insert the OCR result and change the document to `COMPLETED` atomically.

If step 5 observes that another result for the same key already exists, compare only safe metadata. Treat an equivalent already-committed result as idempotent success. Never overwrite differing OCR text silently; raise a stable internal consistency failure without placing either text in an exception or log.

The current deployment has one consumer and one OCR permit, but correctness must not depend solely on that operational fact. Preserve database uniqueness and optimistic-lock handling.

## Deterministic document order

Process documents in the existing ZIP sequence order, with document UUID as a deterministic tie-breaker if needed.

- Do not depend on repository default ordering.
- Do not process documents in parallel.
- Do not use parallel streams, virtual-thread fan-out, Reactor, or `CompletableFuture` fan-out.
- On the ordinary success path, call `FirstPageOcrService.recognize` exactly once for every document that lacks a version-1 result.

## Idempotency and partial progress

RabbitMQ delivery remains at-least-once. Implement these exact semantics:

- A completed version-1 result is never OCRed again on redelivery.
- If three documents are complete and the fourth fails, the first three results remain committed.
- A retry or redelivery resumes at the first incomplete document in sequence order.
- A document left `PROCESSING` without a version-1 result after a crash is treated as stale work and may be processed again.
- A document marked `COMPLETED` but missing its version-1 result is inconsistent; repair its status to `PENDING` and process it rather than skipping it.
- A version-1 result whose document status is not `COMPLETED` is authoritative durable evidence; repair the status to `COMPLETED` and skip OCR.
- A crash after the remote OCR response but before database commit may cause that one OCR call to repeat. Do not claim exactly-once remote execution.

Preserve Task 6's deterministic PDF/storage identities and extraction idempotency. Do not delete already extracted PDFs or completed OCR results when a later document fails.

## Status transitions

Reuse the existing enum values and database constraints. The intended transitions are:

### Document

```text
PENDING -> PROCESSING -> COMPLETED
                      -> PENDING on a retryable failure
                      -> FAILED on a terminal failure
```

`COMPLETED` must never regress during normal redelivery.

### Ingestion job

```text
PENDING -> PROCESSING -> COMPLETED
                      -> remains retryable until the configured attempt limit
                      -> FAILED on a non-retryable failure or exhausted retries
```

### POS record

```text
PENDING/PROCESSING -> REVIEW_REQUIRED after every document has version-1 OCR
                   -> FAILED on terminal workflow failure
```

Do not mark the POS record `COMPLETED`; Task 10 will own structured extraction and later review semantics.

Move the existing Task 6 success transition so it occurs only after all documents have durable version-1 OCR results. Do not briefly publish a false final state between extraction and OCR.

If the exact existing enum uses an equivalent established name, preserve that name rather than adding a synonym. If `REVIEW_REQUIRED` is genuinely absent, add it consistently to the Java enum, SQLite check constraint through the new migration, generated/API mapping where compilation requires it, and tests. Do not edit the OpenAPI contract merely to expose this internal transition.

## Failure and retry policy

Do not retry inside `FirstPageOcrService`, `LlamaCppOcrClient`, or the new workflow service. RabbitMQ remains the sole retry owner.

### OCR failures

Use `OcrException.retryable()` exactly:

- Retryable OCR failures return the current document to `PENDING`, preserve completed earlier documents, and enter the existing bounded RabbitMQ retry path.
- Non-retryable OCR failures mark the current document, job, and POS record `FAILED` and go directly to the existing terminal/DLQ path without consuming pointless retry attempts.

### Rendering failures

Use the stable Task 7 error classification. Implement one exhaustive centralized mapping if `RenderingException` does not already expose a retryable flag:

- Interrupted and temporary storage/I/O unavailability are retryable.
- Missing/corrupt/encrypted/invalid/oversized/unsupported PDF or invalid rendered output is terminal.
- The switch must name every existing Task 7 error code and have no permissive `default` that accidentally makes a new code retryable.

### Other failures

- Database contention or temporary infrastructure failure remains retryable under the existing bounded policy.
- Programming errors and invariant violations must not be converted into successful acknowledgements.
- Reuse Task 6's terminal recoverer and relationship verification. Do not create a competing recoverer.
- Preserve the existing maximum-attempt count, backoff settings, attempt-count semantics, publisher confirms, and DLQ routing.
- Terminal state persistence must occur before the message is finally dead-lettered.

Persist only stable error codes and fixed sanitized messages through the existing job fields. Never persist or log:

- OCR text
- response JSON
- image bytes or base64
- PDF contents
- filesystem paths
- remote response bodies
- names, policy numbers, or eRef values

## Completion rules

Before marking the job successful, verify in a transaction that:

- the record still exists and is active;
- at least one persisted `pos_document` belongs to it;
- every associated document has status `COMPLETED`;
- every associated document has exactly one version-1 OCR result;
- the count of version-1 OCR results equals the count of associated documents.

Then atomically:

- mark the ingestion job `COMPLETED`;
- clear its existing error code/message fields;
- move the POS record to `REVIEW_REQUIRED`;
- update existing timestamps and optimistic versions using the repository's conventions.

Do not include OCR text in the completion query.
