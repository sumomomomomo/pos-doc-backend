## Objective

Put an authentication and authorization boundary around the backend before Task 12 builds the frontend.

Task 11 must provide:

1. Interactive Google OpenID Connect login through Spring Security.
2. A fail-closed allowlist keyed by Google's stable `sub` claim.
3. `USER` and `REVIEWER` application roles.
4. A server-side browser session with secure cookie and CSRF protection.
5. JSON `401`/`403` Problems for API requests rather than HTML redirects.
6. Authenticated current-user/session discovery for the future frontend.
7. Protected, ownership-checked streaming access to an extracted PDF and the original ZIP.
8. Replacement of the placeholder uploader with the authenticated stable subject.
9. Exact-origin CORS support for an explicitly configured frontend, with same-origin deployment remaining preferred.
10. Portable automated tests that never contact Google or the LAN OCR service.

The backend currently listens on port `18080`. The OCR server remains the separate LAN service at `http://192.168.1.34:8080`. Task 11 must not alter either responsibility or confuse the two ports.

## Architectural decisions â€” do not substitute another auth design

### Browser session, not an application-issued JWT

Use Spring Security OAuth2 Client/OIDC login and a server-side `HttpSession`.

- Google authenticates the user.
- The backend stores the authenticated principal in its server-side session.
- The browser receives only the opaque session cookie.
- Do not mint an application JWT.
- Do not place Google ID/access tokens in local storage, session storage, JavaScript variables, URLs, response bodies, or logs.
- Do not send a Google token as the normal API credential.

This is a single-instance application. Spring's in-memory session store is acceptable in Task 11. A backend restart may log users out. Do not add Redis, Spring Session JDBC, or another datastore.

### Same-origin production deployment

The intended production shape is:

```text
Browser -> HTTPS reverse proxy -> frontend and this backend under one public origin
                             -> backend HTTP port 18080 on the trusted network
```

Google's redirect URI must use the public HTTPS origin, for example:

```text
https://<configured-public-host>/login/oauth2/code/google
```

Do not register or document `192.168.1.34:8080` as an OAuth redirect. That address is the OCR server, not this backend. Do not expose MinIO, RabbitMQ, SQLite, or the OCR service to the browser.

## OpenAPI changes

### Security scheme

The current OpenAPI document declares a bearer JWT that the application does not issue. Replace it with the actual session credential:

```yaml
securitySchemes:
  cookieAuth:
    type: apiKey
    in: cookie
    name: POSDOCSESSION
    description: Opaque server-side session established by Google OIDC login.
```

Change the document-level security requirement to `cookieAuth`. Do not retain `bearerAuth` as a production alternative.

Spring's interactive authorization and callback endpoints are framework endpoints:

- `GET /oauth2/authorization/google`
- `GET /login/oauth2/code/google`

Document them in README, but do not add fake generated controller implementations for them.

### Authentication API

Add an `Authentication` tag and exactly these generated operations:

#### Current session

```text
GET /auth/me
operationId: getCurrentUser
success: 200 CurrentUser
errors: 401, 500
```

`CurrentUser`:

```text
additionalProperties: false
required: [email, displayName, roles]
email: string, format email, maxLength 320
displayName: string, minLength 1, maxLength 256
roles: unique array containing USER and/or REVIEWER
```

Do not expose the Google `sub`, access token, ID token, refresh token, claim map, session ID, or cookie value in this DTO.

The `GET /auth/me` response must have `Cache-Control: no-store`. Accessing it must cause the production CSRF token cookie to exist so Task 12 can immediately make protected mutations.

#### Logout

```text
POST /auth/logout
operationId: logoutCurrentUser
success: 204, empty body
errors: 401, 403, 500
```

The production Spring Security logout filter may consume this route before the generated controller method. If so, still keep a generated-interface implementation as a compile-time contract fallback, and prove through a filter-chain integration test that the actual HTTP route invalidates the session, clears `POSDOCSESSION`, and returns `204`.

Logout requires a valid CSRF token.

### Protected binary content

Add these operations to the existing POS-record paths.

#### Extracted PDF

```text
GET /pos-records/{posRecordId}/documents/{documentId}/content
operationId: getPosDocumentContent
success: 200 application/pdf, binary body

```

#### Original ZIP

```text
GET /pos-records/{posRecordId}/source-archive/content
operationId: getPosSourceArchiveContent
success: 200 application/zip, binary body
errors: 401, 403, 404, 503, 500
```

Use OpenAPI `type: string`, `format: binary`. Inspect the generated Spring signature and implement that signature; do not guess or handwrite a conflicting mapping.

Add a reusable `503 ServiceUnavailable` Problem response if absent.

## Google OIDC authentication

Configure exactly one client registration named `google` with scopes:

```text
openid, profile, email
```

Use Spring Security's Google provider metadata and ID-token validation. Do not manually decode an unsigned JWT.

After Spring validates the OIDC response, perform these application checks before creating an authorized session:

1. Issuer is Google's configured/validated issuer.
2. `sub` is present and nonblank.
3. `email` is present and syntactically usable for display.
4. `email_verified` is exactly true.
5. `sub` occurs in the configured viewer or reviewer set.

Reject any failure with `OAuth2AuthenticationException` using a stable internal category such as `user_not_allowed`. The browser-facing failure path must not include the email, subject, token, or raw claims.

Build granted authorities from the allowlist, not from a client-supplied header and not from Google group claims.

Do not log:

- OIDC claims
- authorization codes
- Google tokens
- subject IDs
- email addresses
- names
- session IDs or cookies

Safe logs may contain only a stable authentication outcome category and a generated trace/correlation ID.

## Session and cookie behavior

Production settings:

- Session cookie name: `POSDOCSESSION`
- `HttpOnly: true`
- `Secure: true`
- `SameSite: Lax`
- Cookie path: `/`
- Session timeout: 8 hours of inactivity
- Session fixation protection enabled
- No session ID in URLs
- Logout invalidates the server session and deletes the session cookie

Set `server.forward-headers-strategy=framework` so redirects and secure URLs work behind the HTTPS reverse proxy. Document that the reverse proxy must overwrite, not append untrusted forwarded headers and must not expose port `18080` publicly.

Do not set `SameSite=None` unless a later, explicit cross-site deployment requires it. The intended deployment is same-origin.

## CSRF behavior

Production authentication uses cookies, so CSRF protection is mandatory for state-changing requests.

Use `CookieCsrfTokenRepository` with:

- cookie name `XSRF-TOKEN`;
- header name `X-XSRF-TOKEN`;
- CSRF cookie readable by JavaScript;
- secure cookie in production;
- path `/`.

Keep the session cookie HttpOnly. Only the CSRF cookie is JavaScript-readable.

Ensure a successful authenticated `GET /auth/me` materializes the deferred token and sends the CSRF cookie. Use the established Spring Security SPA request-handler/filter pattern rather than generating a token manually.

CSRF is required for:

- upload;
- PATCH;
- verification;
- delete;
- logout.

`POST /pos-records/search` is read-only and may be excluded from CSRF so a read-only client can search after authentication without manufacturing a state-changing token. Document and test this sole API exception. Do not disable CSRF globally in Google mode.

An invalid/missing CSRF token returns a sanitized `403 application/problem+json` for API paths.

## API authentication and authorization failures

For requests under the API context:

- unauthenticated access returns `401 application/problem+json` with stable code `AUTHENTICATION_REQUIRED`;
- authenticated but unauthorized access returns `403 application/problem+json` with stable code `ACCESS_DENIED`;
- CSRF rejection returns `403 application/problem+json` with stable code `CSRF_TOKEN_INVALID`.

Bodies must use the generated `Problem` schema and fixed PII-free details. Do not redirect an API request to Google's login page.

The explicit browser navigation to `/oauth2/authorization/google` is the only login-start action and should redirect normally.

## Protected document/archive content service

Implement a thin persistence lookup followed by storage streaming. Do not create a presigned URL.

### Authorization and IDOR protection

For a PDF request:

1. Load the active POS record by `posRecordId`.
2. Load `documentId` using a repository query that also requires that exact parent record and active parent.
3. Return `404 DOCUMENT_NOT_FOUND` when either ID is missing, deleted, or the document belongs to another record.
4. Never reveal through error differences whether a document exists under another record.

For a ZIP request:

1. Load the active POS record.
2. Resolve only its persisted `sourceArchive` relationship.
3. Return `404 POS_RECORD_NOT_FOUND` for a missing/deleted record.

Never accept a bucket or object key from the HTTP request.

### Transaction boundary

Inside a short read-only transaction, produce an immutable internal descriptor containing:

- storage object ID;
- internal object key;
- trusted content type;
- trusted original filename;
- expected byte size.

End the transaction before contacting MinIO. Opening or copying a MinIO stream must not occur inside a database transaction.

### Streaming

Reuse and minimally extend `MinioObjectStorage` rather than creating a second MinIO client.

- Stream the object; do not load the complete ZIP/PDF into a byte array.
- Ensure the MinIO response stream closes when HTTP response processing finishes or fails.
- Do not write downloads into the application work directory.
- Do not create a public URL.
- Do not support byte ranges in Task 11; omit `Accept-Ranges` and return normal `200` bodies.

Response headers:

| Content | `Content-Type` | `Content-Disposition` |
|---|---|---|
| PDF | `application/pdf` | `inline` with safe UTF-8 filename |
| ZIP | `application/zip` | `attachment` with safe UTF-8 filename |

Also set:

- exact persisted `Content-Length`;
- `Cache-Control: no-store, no-cache, must-revalidate`;
- `Pragma: no-cache`;
- `X-Content-Type-Options: nosniff`.

Build `Content-Disposition` using Spring's safe builder. Reject or sanitize CR, LF, NUL, path separators, and invalid filenames; never concatenate raw filenames into a header.

The intake path already validates types. Nevertheless, refuse to serve a PDF descriptor whose trusted metadata is not PDF or a source descriptor that is not ZIP. Treat that as an internal invariant failure.

### Storage failures

Map failures before response commitment as follows:

- temporary MinIO connectivity/timeout -> `503 DOCUMENT_STORAGE_UNAVAILABLE`;
- persisted metadata pointing to a missing/inconsistent object -> `500 DOCUMENT_CONTENT_UNAVAILABLE`;
- record/document lookup or parent mismatch -> the `404` codes above.

Use fixed details. Do not include bucket, key, filename, endpoint, MinIO response body, or exception message. A mid-stream network failure may result in a truncated connection after headers are committed; close resources and log only the stable category plus safe UUIDs.
